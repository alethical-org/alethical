Part 1 · measured today

What this repository actually looks like

There is exactly 1 branch that lives forever here: main. Everything else is temporary. A branch is cut from main, gets one topic of work, becomes a pull request, and is squashed back into main as a single commit before being deleted. That pattern is called trunk based development, and 971 pull requests have gone through it.

What is working

Short branches. Work leaves main and comes back the same day, so nobody spends an afternoon untangling 2 versions of the same file. 28 pull requests merged in the last 24 hours, and the 3 newest open ones are 0 or 1 commits behind main.

What is not

53 of the 64 shared branches never merged into main and never will. The worst is feat/rag-chat, which sat still while main moved 987 commits ahead of it. Anyone who opens that branch is reading a version of this product from 3 months ago, and there is nothing on the branch to tell them so.

6 open pull requests are more than 240 commits behind main. A pull request that far behind is not really a proposal any more: it is a guess about a codebase that no longer exists. The fix is a habit, not a tool. Rebase it onto current main and merge it, or close it and say why.

178 branches on this laptop have already been merged and can be deleted today. They are noise in every branch list, every autocomplete, and every search for "which branch was that on".

Part 2 · the reference flow

Dev, staging, production, and features

Now the model to learn. Instead of 1 permanent branch there are 3, and each one mirrors a running copy of the software. Code is only ever promoted upward, one step at a time, so every change is exercised in a real environment before it reaches a real person.

The point of the extra branches is not tidiness. It is that develop, release, and main each have an actual deployed website behind them, and a change has to survive each one before it gets to the next.

feature/*

One branch, one topic, cut from develop and merged back into develop. Never cut a feature branch from another feature branch: your pull request then contains someone else's unreviewed work.

lives hours to a few days · no environment of its own

develop

Where finished features meet each other for the first time. This is the branch that answers "do these 6 changes still work together". It is expected to break sometimes, and that is what it is for.

permanent · deploys to the dev site automatically

release/1.4

Cut from develop when a release is feature complete. From that moment it takes bug fixes only. New features keep landing on develop for the release after this one, so nobody has to stop working while testing happens.

lives days to weeks · deploys to staging, where QA signs off

main

Exactly what is live for real people, and nothing else. Nobody commits to it directly. Every commit on it is a merge from a release or a hotfix, and every one gets a version tag so you can name and roll back to any past release.

permanent · deploys to production · tagged v1.4.0, v1.4.1

hotfix/*

The only path that skips the queue, for when production is broken right now. Cut from main, not from develop, so it carries the fix and nothing else. Merge it into main and then into develop as well.

lives hours · tests on staging before production if there is any time at all

Part 3 · the honest comparison

Which of the 2 should you use

Both graphs above are correct practice. They solve different problems, and the choice is really a question about your release rhythm, not about tidiness.

what this repo runs today

Trunk based

  • 1 permanent branch. Short branches off it, squashed back in.
  • Nothing waits. 28 changes reached real people in the last 24 hours.
  • Branches live hours, so merge conflicts stay small.
  • Safety comes from automated checks and small changes, not from a staging queue.
  • Costs you this: there is no rehearsal environment holding a full release, so a bad change reaches production and gets fixed forward.
the reference model above

Dev, staging, production branches

  • 3 permanent branches, each mirroring a deployed environment.
  • A human can sign off on a whole release on staging before anyone sees it.
  • Version tags make "roll back to last Tuesday" a real, 1 command answer.
  • Costs you this: a finished change can wait days for the next release.
  • And this: the same fix has to be merged in 2 or 3 places, which is the step people forget and the reason fixes come back from the dead.

Pick the second one when a release needs human sign off, when you ship on a schedule rather than continuously, or when a broken production is expensive enough that a rehearsal is worth the delay. Pick the first when you can make releasing boring enough to do 28 times a day. The mistake is running the second model's branch names with none of its discipline: a develop branch that nothing deploys, and a staging branch nobody tests, buy the delay without the safety.

Part 4 · habits

The 5 habits that keep either graph clean

These are in order on purpose. Each one only works if the one before it held.

  1. Start from the branch you will merge back into

    Cut a feature branch from develop, a hotfix from main. Cutting from wherever your laptop happened to be pointing is how someone else's half finished work ends up inside your pull request.

  2. One topic per branch, named so a stranger can guess it

    feature/bill-search-filters tells the next person what is in it. fix-stuff and my-branch-2 do not, and a branch nobody can identify is a branch nobody dares delete. That is exactly how this repo reached 53 abandoned ones.

  3. Bring the base to you every day, not once at the end

    Run git fetch origin and rebase onto your base branch daily. Conflicts are cheap when they are 1 day wide and brutal when they are 987 commits wide. This single habit is the difference between the blue arcs and the grey dead ends in the first graph.

  4. Re-run the checks after the base moves

    A green checkmark is a statement about the code your branch was tested against. If the base branch moved since then, that statement has expired. Two changes can each pass alone and fail together, and this has already happened here: a change removed a database write while another added a test asserting that exact write. No file conflicted, both were green, and the trunk broke.

  5. Delete the branch the moment it merges

    Its commits are safely on the base branch, so nothing is lost. Turn on the repository setting that deletes the remote branch automatically, then prune your own copies. 178 already merged branches are sitting on this laptop right now.

Part 5 · the commands

Doing it, in the reference flow

Start a feature. Note that the base is named explicitly, so it does not matter which branch you were on:

# 1. get the real state of the shared branches first
git fetch origin

# 2. branch from develop, explicitly, and name the topic
git switch -c feature/bill-search-filters origin/develop

# 3. work, committing in small pieces
git add -p
git commit -m "Add chamber filter to bill search"

# 4. every morning, bring develop to you
git fetch origin
git rebase origin/develop

# 5. push and open the pull request against develop
git push -u origin feature/bill-search-filters
gh pr create --base develop

Promote a release. The release branch is cut once, then only ever receives fixes:

# cut staging from develop when the release is feature complete
git switch -c release/1.4 origin/develop
git push -u origin release/1.4

# QA finds a bug: fix it on the release branch, not on develop
git switch release/1.4
git commit -m "Fix empty filter state on staging"

# ship it: into production, tagged
gh pr create --base main --head release/1.4
git switch main && git pull
git tag -a v1.4.0 -m "Release 1.4.0"
git push origin v1.4.0

# then merge back down, or the next release undoes the QA fixes
gh pr create --base develop --head release/1.4

Clean up. Safe, because --merged only ever lists branches whose work is already in the base branch:

# which of my local branches are already merged, and so deletable
git branch --merged origin/main

# delete them (-d refuses anything unmerged, unlike -D)
git branch --merged origin/main | grep -v '\*' | xargs -n 1 git branch -d

# forget remote branches that no longer exist on the server
git fetch --prune

Part 6 · reading a repo yourself

How the numbers on this page were measured

Run these in any repository to see its real shape rather than its intended one. Every figure above came from them.

# how many shared branches never came back (53 here)
git branch -r --no-merged origin/main | wc -l

# how many of your local branches are finished and deletable (178 here)
git branch --merged origin/main | wc -l

# how far behind the trunk each unmerged branch has drifted
for b in $(git branch -r --no-merged origin/main | grep -v HEAD); do
  echo "$(git rev-list --count $b..origin/main) behind  $b"
done | sort -rn | head

# the shape of the trunk itself: linear, or a thicket
git log --graph --oneline -20 origin/main
  • The number that tells you the most

    How far behind the trunk your oldest open branch is. Under 20 means the team merges. In the hundreds means branches are being opened and forgotten, and no amount of process will fix that until the habit changes.

  • The number that lies

    Total branch count. 408 branches on this laptop sounds alarming and mostly is not: 178 are finished work awaiting cleanup, and none is older than 30 days. Split the count by merged and unmerged before drawing any conclusion from it.
