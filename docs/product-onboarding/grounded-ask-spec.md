Status: draft for engineering review
Owner: Eugene
Related surfaces: signed-out home (hero), chat

The signed-out hero ships three sample question chips that map 1:1 to the shipped answer paths (bill text · topic → bills · topic → legislators), with the Ask box showing the current placeholder copy (§2). There is no vote chip — the vote path is not built yet (see §2, Build order).

## 1. Goal and the promise this build protects

The signed-out home page hero ships this copy:

> **Grounded answers on Minnesota law**
> We read every bill so you don't have to — what it says, where it stands, and how legislators voted. Plain language, every answer linked to its official source.

The subhead is a contract, not marketing: **no answer ships without a resolvable citation to its official source.** Everything in this spec exists to keep that sentence true when the hero's Ask box goes from bill-scoped chat to a general question box.

**Corpus currency is part of that promise.** Every answer path below can only surface what ingestion has pulled in, so "what it says, where it stands" presumes the *current* legislative session is in the corpus — and **current means fresh, not just present**. Verified against production (Jul 14, 2026): 2026-session bills including **HF 4138** (the answer to the canonical question **"What's in the new social media law for kids?"**, already a router few-shot in `alethical/api/services/ask_router.py`) are ingested *and* AI-enriched — the Revisor search returns the whole biennium, so bills arrive regardless of the configured session year — but ingestion runs are human-triggered and `only_missing` by default, so an already-ingested bill's status/text/actions go stale: production held HF 4138 at a pre-passage status ("placed on Calendar", `in_committee`) two months after it was signed into law. A status-stale answer misframes "this law *requires*" as "this bill *proposes*" (§9.2) — a currency failure even with the bill present. **Resolved on the data side ([#155](https://github.com/alethical-org/alethical/issues/155), closed Jul 24, 2026):** the full 94th-biennium corpus was re-fetched Jul 14–22 (10,530 bills) and re-enriched on real embeddings, and HF 4138 now reads as *enacted law*. The remaining end-to-end check — asking the canonical question through the Ask surface and confirming the framing — moved to [#79](https://github.com/alethical-org/alethical/issues/79), since it needs that surface to run. Currency is a standing property, not a one-time fix: ingestion is human-triggered and `only_missing` by default, so the same staleness returns if a session is left unrefreshed. Currency-implying hero copy and chips must stay within what the corpus can *freshly* answer. Durable invariant: `.claude/rules/grounded-answers.md` rule 7 (Answerable means ingested — keep the corpus current).

## 2. User-facing behavior

A signed-out visitor types a natural-language question into the hero Ask box. The system classifies the question, answers from ingested Minnesota data with citations, or honestly declines.

The hero placeholder reads **"Ask about bills or legislators by issue or name"** — no trailing ellipsis, which this line and the checklist below both added. (This copy will land when the Ask hero ships; the interim signed-out-home Ask entry field that prototyped it as `ASK_PLACEHOLDER` in `HomeSignedOutScreen.tsx` was removed, because free-form Ask is roadmap, not built — the home now routes to Search Bills and Find My Legislator instead.) The grammar is deliberate: bills and legislators are the only *destinations* the sentence promises; "by issue or name" are *entry points* (issue → the two topic paths; name → a legislator's profile via directory match — §4.6, records navigation, not a generated answer), never a third entity type — there are no issue-level answers (no issue pages, no cross-corpus issue summaries). Entry points are ordered by what a layperson actually arrives with: most think in issues or keywords, some know a legislator's name, almost none know a bill's name or number — so bill names are deliberately *not* advertised as an entry point (and "issue" doubles as the keyword case). Deliberately no "votes" — the vote path is not built yet (see Build order below). The placeholder must never advertise an intent the router can't answer. Because this copy actively steers users toward arbitrary topics, the retrieval-relevance threshold and NO MATCHES state (§4.5) must ship before it does.

### Acceptance scenarios (the hero's sample chips — these are the tests)

| # | Question | Expected behavior |
|---|----------|-------------------|
| 1 | **What's in the cannabis legalization bill?** *(also handles an HF/SF number, e.g. SF 2310, or a recognizable bill title)* | Resolve to the bill via fuzzy title match, then a bill-text RAG answer using the existing pipeline, with citations to the retrieved passages and the bill's official page. Deliberately phrased without a bill number to prove you don't need one; if the phrase is ambiguous, fall back to the topic → bills list (scenario 2). **One bill per answer:** `bill_text` prose is always scoped to a single resolved bill. Broad cross-bill questions ("what has Minnesota done about housing?") are topic questions — they route to scenario 2, never to a prose answer synthesized across multiple bills (§7, [#87](https://github.com/alethical-org/alethical/issues/87)). |
| 2 | **What bills affect healthcare?** | List of current-session bills matching the topic (policy-area tag and/or keyword match), each with its AI summary line and a citation link to the bill's official page. |
| 3 | **Which legislators support affordable housing?** | Legislators who **authored or co-authored** bills matching the topic, with per-legislator bill counts and links to each legislator profile and the underlying bills. See framing rule in §4.3 — "support" must be reported as authorship/votes, never as inferred opinion. |
| 4 | *Vote question (e.g., "How did my legislator vote on cannabis?")* | **Today — honest deflection** — the router recognizes the intent and answers: vote-by-vote answers are coming soon, and every roll call is already on the bill's page (deep-link the bill's Votes tab when the bill resolves — §9.3). Never a partial or unverified vote answer. **Once the vote path ships — the full cited answer** — vote position, tally, date, citation to the roll call's official record; if no roll call exists, say so and offer the chamber tally or bill status. |
| 5 | *Out of scope question (e.g., federal bill, statute lookup, "is this bill good?")* | Polite refusal that names what we do cover. No hallucinated answer. |

Every answer ends with tappable citations using the existing citation panel pattern (excerpt + highlighted passage where applicable + "Open official source").

### Build order — what is live, and what the vote path waits on

**Live today:** router (§4.1) · bill-text RAG path · topic → bills · topic → legislators · refuse + vote deflection (§4.5) · generalized citation URLs (§4.4) · **bill** resolution for generated answers (HF/SF-number regex + fuzzy title match) plus legislator-name → profile navigation (§4.6) · Answer page UI states (§9) · Votes tab tally + deep link (§9.3).

**Not built yet — the vote path, gated on the §5 coverage spike:** the `legislator_vote` answer path · person entity-resolution (§4.6) · the "my legislator" location prompt (§8.1) · the vote chip returns to the hero — in chamber-tally form first if individual-vote coverage turns out thin.

Rationale: the vote path stacks the three hardest problems (person resolution, roll-call coverage, signed-out location capture), while every shipped path is a thin formatter over queries that already exist. Roll calls are already live on the bill page's Votes tab, so the hero's "how legislators voted" stays true product-wide — users can *see* every vote; conversational vote answers arrive with the vote path.

## 4. What to build

### 4.1 Question router
Classify each Ask into: `bill_text` (scenario 1) · `topic_bills` (scenario 2) · `topic_legislators` (scenario 3) · `legislator_vote` (scenario 4) · `refuse` (scenario 5). Bounded LLM classification step; low temperature; the router's output is a typed intent, not free text. All five intents are classified today — `legislator_vote` maps to the deflection response (§4.5) until the vote path ships.

There is deliberately **no `chat` intent** (confirmed Jul 14, 2026, resolving the 4-intent shipped router's `chat` catch-all): the router only ever produces a one-shot answer page. Chat is a *continuation* surface — entered from a bill page or from a `bill_text` answer's signed-in follow-up composer (§9.2) — never a classification destination. Durable invariant: `.claude/rules/grounded-answers.md` rule 8 (Follow-up chat is a standing capability).

### 4.2 Structured-answer formatters (2–3 thin functions)
Each takes existing query results and produces a plain-English answer **plus a citations array** in the same shape `me.py` already emits (`citation_label`, `excerpt`, `url`, …):
- `topic_bills`: policy-area + keyword match → bill list with AI summary lines; cite each `Bill.official_url`. Return the **total match count** (the UI shows "6 of 23"). Order by **legislative progress** (signed into law → passed chamber → in committee), secondary sort by most recent action date — ordering must be deterministic so a shared `?q=` link re-renders identically. Cap the displayed list at ~6; overflow routes to Search pre-filtered to the topic.
- `topic_legislators`: join topic-matched bills → `Sponsorship` → legislators; cite `Legislator.profile_url` + underlying bills. Displayed counts map from `SponsorshipRole`: `chief_author` → **"Authored"**, `co_author` → **"Co-authored"** (Minnesota Legislature terminology — the UI never says "co-sponsored"). The `sponsor` role and committee-target rows need their semantics confirmed in the §5 spike before they count toward either number. Group by chamber; sort by count descending.
- **(not built yet)** `legislator_vote`: resolve legislator + topic → `VoteRecord` via `/legislators/{id}/votes` join; cite `VoteEvent.official_url`. Fallback ladder: individual vote → chamber tally (VoteEvent counts parse even when names don't match) → bill status.

### 4.3 Framing rule for "support" (scenario 3)
Grounded neutrality: the answer must say what the record shows — "authored or co-authored N bills on affordable housing," "voted yes on HF xxxx" — never "supports affordable housing" as an opinion claim. The word "support" in a user's question is interpreted as *authorship/co-authorship and/or yes-votes* and the answer says so explicitly. On the Answer page this interpretation is **fixed UI copy, not LLM output** (§9.4) — if the model writes the sentence, it will eventually drift; the layout owns it.

### 4.4 Generalized citation source URLs
Today `me.py` hardcodes `url = bill.official_url`. Generalize: citation URL is chosen per source type — bill → `Bill.official_url`, roll call → `VoteEvent.official_url`, legislator → `Legislator.profile_url`. No citation without a resolvable URL.

### 4.4a How much of a resolved bill an answer reads (decided [#868](https://github.com/alethical-org/alethical/issues/868), Jul 31 2026)

Once a `bill_text` question has resolved to one bill, retrieval is no longer searching a corpus by meaning — it is deciding **how much of one known document** to read. Two shapes, chosen by what the question asks for:

- **A specific question** ("when does this take effect?") keeps the fixed sample of **4** passages. Four is the right size, and feeding a hundred would cost money and make every reader wait for nothing.
- **An enumerate-everything question** ("which / list / all / every / how many …") reads as much of the bill as a **20,000-word budget** allows, in relevance order.

**Why a budget rather than a bigger fixed number.** Measured over all 10,433 production bills with retrievable text (Jul 31 2026): median **302 words** / 2 passages, 90th percentile 2,339, 99th percentile 20,977, largest 241,551. The median bill is *already* read in full by the fixed sample; 20,000 words reads **99%** of bills in full; the ~1% that overflow are the omnibus bills. A budget spends nothing on the common case and only opens up where the question needs it.

**Why not keyword search inside the bill.** Postgres full-text ranking over the resolved bill's passages was the obvious alternative, and it was ruled out on the thing that matters rather than on taste: for an enumerate-everything question there is no "best four" to find, because the seventy passages that each say "for a grant to the city of X" are all equally on-topic. Better *selection* cannot make a sample complete — only reading more can, or saying it was a sample. Since the budget already reads 99% of bills in full, keyword ranking would change only *which* incomplete passages the remaining 1% shows, and those answers are flagged partial either way. Hybrid retrieval stays [#380](https://github.com/alethical-org/alethical/issues/380)'s ground, where it is measured against the retrieval eval instead of added here on intuition.

**Cost and wait, measured live on HF 719** (102 passages, ~30,000 tokens of context, `gpt-4o-mini`): **$0.0002 → $0.0048** per answer, and **~4s → ~11s** with a worst observed 25s. Roughly 24× the cost of one answer on a base of two hundredths of a cent, landing only on list questions on long bills. Which model writes answers is [#865](https://github.com/alethical-org/alethical/issues/865)'s decision; whichever it picks, **price the omnibus list question, not the median** — the worst-case input is ~30,000 tokens against ~900 before.

**What this does not fix, and must not be read as fixing.** Reading the whole bill did not make the answer complete: given all 102 passages, `gpt-4o-mini` listed 26–35 of HF 719's 98 cities across three runs. That is the same finding the #865 eval reached from the other end (overclaim rate flat at 80% / 89% / 80% across 4, 8 and 16 passages — `docs/product-onboarding/answer-quality-bar.md` §9), and it is why the budget is **not** presented as the fix for honesty. It buys *completeness where completeness is affordable*; honesty comes from §9.5 decision 11's note and the two answer-path guards below.

### 4.5 Cite-or-refuse guardrail (router level)
Extend the existing empty-retrieval fallback into a hard invariant for every answer path:
- Every answer must carry ≥ 1 citation with a resolvable URL, or the system refuses.
- **No answer may say a bill omits something when only part of the bill was read, and no answer may claim its own list is the whole set** ([#868](https://github.com/alethical-org/alethical/issues/868)). Enforced in the answer path, not only requested in the prompt — the shipped bug was a model doing exactly as instructed. The durable statement of both, and why they are gated differently, is `.claude/rules/grounded-answers.md` rule 11.
- Add a retrieval-relevance threshold so weak matches refuse rather than stretch.
- Out-of-scope classes (federal, statutes, opinion/prediction, open web) refuse with a one-line statement of what Alethical does cover.
- **No-matches (current behavior):** an in-scope topic with zero (or below-threshold) matching bills gets the **NO MATCHES** response — "No current-session bills match *{topic}*" + a Search link. **No chips and no heading**, contrary to what this said: the shipped state (`AskAnswerScreen.tsx`) renders body text and one link, and the string "THINGS YOU CAN ASK" exists nowhere in the frontend. This is a distinct state from out-of-scope refusal (§9.1): in scope, just empty. A zero-result answer has nothing to cite, so it must never render as a normal answer.
- **Vote deflection (current behavior):** questions classified `legislator_vote` get an honest not-yet — vote-by-vote answers are coming soon, and every roll call is already on the bill's page (deep-link the Votes tab when the bill resolves, §9.3; when the bill doesn't resolve, degrade to the `topic_bills` list with each card linking to its Votes tab). Never a partial or unverified vote answer, and **no tallies or vote positions on the deflection page itself** — those are records and live on the Votes tab.

### 4.6 Entity resolution
**Answer-scoped resolution is bills only:** HF/SF-number regex plus fuzzy title match (via `/search`). `topic_legislators` reaches legislators through sponsorship joins, not name lookup, so no per-person resolution feeds a *generated answer* in v1.

**Live — legislator name → profile (records navigation, not an answer):** a query that resolves to a known legislator name routes to that legislator's **profile page** — a records surface (grounded-answers rule 4), so it sidesteps the cite-or-refuse contract. It reuses the substring `full_name` match that already exists (`GET /legislators?q=`, `GET /search?types=legislators` — `alethical/api/routers/public.py`): exactly one match → open the profile; multiple → a disambiguation list (or route to Search Legislators pre-filtered on the query); zero → the NO MATCHES state (§4.5) with a Search link. **Matching is already typo-tolerant, not substring-only** — this line said the opposite for months. `GET /legislators?q=` runs `keyword_search_clause` (`alethical/api/routers/public.py`), which matches a raw substring, a stemmed root, *and* trigram word-similarity for words of 5+ letters (`_MIN_FUZZY_WORD`), so a misspelled name of any real length resolves today. What is genuinely still missing is **nickname** mapping ("Bob" → Robert), which no code attempts. This is what backs the placeholder's "name" entry point (§2): typing a legislator's name takes you *to them*, it does not synthesize a person-scoped answer. Build delta on [#79](https://github.com/alethical-org/alethical/issues/79) is a thin routing branch over existing endpoints, not new backend.

**The ground an Ask covers is a LEGISLATURE, not a session row (#810, Aug 2026).** Every answer path used to scope to the single `legislative_session` flagged current, which is the 94th's regular session. Minnesota's 94th also sat for a first special session in June 2025, whose 46 bills include 10 chaptered laws — the state's education, health-and-human-services, environment and higher-education budgets — and all of them were invisible to Ask while being readable on their own bill pages. Scope is now every session sharing the current one's `session_number` and jurisdiction, resolved once in `alethical/api/services/legislative_sessions.py` and used by all five paths, so they cannot drift. Prior bienniums ([#359](https://github.com/alethical-org/alethical/issues/359)) carry different numbers and stay out with no extra guard. **Service periods and committees stay pinned to the regular session** — they exist only there (206 and 46 rows, zero for the special session), and that join is what supplies an author's chamber and party.

**A bill number that names two bills is never resolved by preference (#810).** A Legislature numbers its special-session files from 1 again, so "HF 5" is a regular-session tax bill *and* the special session's K-12 education finance act. Three outcomes: the question names a session ("HF 5 in the first special session") and resolves there; the number matches once across the Legislature and resolves; or it matches more than once and the answer is **both bills, offered as a choice**, carrying `ambiguous_reference` so the page says why it is not answering. Preferring the regular session was considered and rejected: it would answer about a tax bill for a reader asking about schools, with every trust signal firing correctly on the wrong bill — the failure mode `.claude/rules/grounded-answers.md` rule 11 exists for. There is no evidence in a bare number to break the tie with, so nothing breaks it (rule 1, cite or refuse). Which session a phrase names is decided by `named_special_session`, the same function the cross-reference resolver uses ([#804](https://github.com/alethical-org/alethical/pull/804)), so "First Special Session" means one thing across the product and an unrecognised ordinal declines rather than widening.

**Each bill says which session it is from, the answer says which Legislature it covered.** The answer-wide `session` always names the ground covered, in every answer shape; a bill payload carries its own `session` only when that is not the Legislature's regular session, which is what the page needs to keep two cards both reading "HF 5" apart. The two never swap meanings depending on the answer.

**Not built yet — tolerant person resolution for answers:** name/nickname → legislator id, tolerant of partial names and misspellings, feeding the `legislator_vote` path and per-person answers. `/search` and the name-matching in `votes.py` (`legislator_keys`, `build_legislator_index`) are starting points. "My legislator" resolution depends on §8.1.

### 4.7 Follow-up chips ("Continue the conversation")
Four rules, enforced by construction rather than review:
1. **Route-live-or-don't-ship.** Every chip targets a live answer path and must not be refusable — a refusal of a question the system itself suggested is the worst trust failure on the page. `bill_text` chips are derived from the answer's own retrieved/cited chunks (the material is guaranteed present), never free-associated. Cross-intent chips are templates filled from the resolved topic: "What other {topic} bills are there?" (`topic_bills`) · "Which legislators authored {topic} bills?" (`topic_legislators`).
2. **Self-contained submit text.** Signed-out chips fire stateless Asks, so a chip may *display* short text ("Can cities opt out?") but *submits* a fully qualified question ("Can cities opt out under the Adult-Use Cannabis Act (SF 2310)?"). Same mechanism signed-in, so behavior doesn't fork.
3. **Same scope-integrity rule as the placeholder (§2).** No vote-phrased chips until the vote path ships, nothing opinion-shaped or how-to-shaped. Cap at 3; order deep-dive → bills → legislators.
4. **Chip click behavior — hero vs. follow-up (decided Jul 2026).** Hero chips **populate the Ask box and focus it** (edit-before-ask; triggers the field's focus state) rather than navigating on click — the populated string is the full, routable question, so pressing Ask unedited still routes cleanly. This populate-only pattern is **hero-only**: follow-up chips here show short display text (rule 2) and must **fire their fully-qualified submit directly**, or a system-suggested chip can land on a refusal (rule 1's worst case). Whatever is submitted — chip or hand-edited — runs through cite-or-refuse / NO MATCHES (§4.5).

## 5. Coverage spike — the vote path's gate (blocks nothing that is live)

Half-day task against the live DB. Runs in parallel with everything else; its findings decide *how* the vote path ships:
1. What share of current-session bills with floor action have legislator-level `VoteRecord`s? (Check `no match` log rate from `votes.py`.)
2. Do policy-area tags + keyword search reliably surface bills for: healthcare, affordable housing, cannabis? *(This half affects the live surface — if a hero chip's topic is weak, tune the keyword backstop.)*
3. *(affects the live surface)* What does the `sponsor` value of `SponsorshipRole` represent in ingested rows (vs `chief_author`/`co_author`), and how common are committee-target sponsorships? Decides whether either counts toward the §4.2 displayed numbers.

**Decision rule:** if individual-vote coverage is thin, the returning vote chip ships in chamber-tally form ("How did the House vote on cannabis?") — still cited, always answerable — and upgrades to individual votes as coverage improves.

## 7. Out of scope

Federal legislation · Minnesota Statutes corpus · opinion, prediction, or "is this bill good?" analysis · open-web retrieval · multi-model consensus. **Cross-bill synthesis** (one prose answer woven from multiple bills' text) is **not built yet but planned** ([#87](https://github.com/alethical-org/alethical/issues/87)) — unlike the permanent exclusions above, which we are never doing; until it ships, such questions get the cited `topic_bills` list. The refusal path names all of these as not-yet-covered rather than pretending.

**Section-level retrieval is not part of this design — decided Aug 2026 ([#715](https://github.com/alethical-org/alethical/issues/715)).** Every answer path retrieves **chunks** (`rag_chunk`, ranked by vector similarity in `semantic_rag_chunk_stmt`, `alethical/db/models.py`); `rag_section_document` exists to hold the cleaned section text those chunks are cut from and to carry citation provenance back to the bill, not as a retrieval unit of its own. That holds for keyword retrieval too: the planned lexical arm ([#380](https://github.com/alethical-org/alethical/issues/380) — Postgres full-text fused with pgvector via Reciprocal Rank Fusion) must rank the *same* units as the vector arm it fuses with, so it indexes `rag_chunk.search_text`. Consequently `rag_section_document.search_text` — a copy of each section's text prefixed with the bill number, bill title and headings, written by every ingest — had no reader and was **dropped** (Alembic `0024_drop_rag_section_search_text`). It cost 91 MB of a 240 MB table and, because it embedded `bill.title`, could hold a stale headline indefinitely with no visible symptom (the drift that [#708](https://github.com/alethical-org/alethical/issues/708) fixed). Anything that needs the prefix rebuilds it from `bill` plus `bill_version_section`. **Do not re-add a section-level text copy** without a query that reads it in the same change.

## 8. Open questions

1. **(with the vote path) "My legislator" on a signed-out page:** trigger the rep-lookup flow inline (address prompt) on first use, or seed the chip with a named legislator until the user runs Find My Legislator / signs in? Leaning: inline prompt reusing `POST /representative-lookups`. Deferred with the vote path — nothing live depends on it.
2. **Answer persistence, predefined questions decided, open beyond them.** Copy link/Share still emit `?q=` links. Topic answers are deterministic DB queries. An exact match to a bill's current `question_prompts` entry reuses one saved public answer ([#1119](https://github.com/alethical-org/alethical/issues/1119)). The key includes the current bill-text version and source fingerprint, current summary row, suggestion position and fingerprint, answer model, embedding model, and an answer-pipeline fingerprint ([#1140](https://github.com/alethical-org/alethical/issues/1140)). That fingerprint covers the complete answer prompt plus the cleaning, chunking, retrieval, coverage, answer-assembly, guard, and citation rules that decide what the model sees and what Alethical serves. Constants are fingerprinted by value; semantic logic changes require an explicit pipeline-version bump. A change to any input generates a fresh answer. Rows saved before #1140 carry the older prompt-only fingerprint and safely miss without a database change, so old and new application releases can overlap without depending on migration order ([#1124](https://github.com/alethical-org/alethical/issues/1124)). The saved payload holds only generated prose, citations, and coverage; live bill status, session, and record date are rebuilt on every read. Simultaneous first visits use one database lock and generate once. A reader-written or edited question is never cached or fingerprinted. Later ([#82](https://github.com/alethical-org/alethical/issues/82)): public-id snapshots can cover other answers and provide an audit trail. Signed-out sessions still don't persist.
3. Model/latency budget for the router step (one extra LLM call per reader-written question; exact public suggestions bypass it).

### 9.5 The chip-reached answer page — decided web design (Jul 31 2026)

Design handoff: `docs/mockups/answer-web/` (README.md · LIVE-answer-spec.md · `LIVE Answer web.dc.html`). Build: [#859](https://github.com/alethical-org/alethical/issues/859). **Where this section and §9.1–§9.2 disagree, this section wins for the `bill_text` state** — those rows describe the first build, which shipped a freeform field, inline numbered citation chips, a "SOURCES" heading and a bottom-of-page Copy link, all of which this design removes.

**Scope.** Signed out only; a suggested-question chip on Bill Detail is the only way in; no question field, no Ask button, no composer, no sign-in gate on the page. This is consistent with [#832](https://github.com/alethical-org/alethical/issues/832) (the homepage question box becomes a roadmap line for launch): after both ship, no reader can hand-author a question, so an answer page cannot be reached by a query that refuses. The auth-gated follow-up model stays deferred ([#137](https://github.com/alethical-org/alethical/issues/137), [#84](https://github.com/alethical-org/alethical/issues/84)); multi-bill answers stay deferred ([#87](https://github.com/alethical-org/alethical/issues/87)).

**Layout.** Nav → answer header on the gradient (back link "← Back to {CODE}", the question verbatim as H1, the meta line `2025–26 LEGISLATIVE SESSION` with **no date**, Share right-aligned, closed by a 1px `rgba(17,21,15,0.1)` rule with content starting **40px** below it) → white body, two columns `1.4fr / 1fr` gap 56px (left: answer, bill card, "Ask another question"; right: the "From the bill" rail, sticky at `top:24px`, collapsing under the main column below 1100px) → the standard source line → footer.

**Decisions taken during review of the handoff.** Each departs from the mockup on the strength of a pattern already shipped elsewhere; the reasoning is recorded here because the mockup file cannot carry it.

1. **The rail shows one card per cited *section*, and that card keeps every one of the section's passages** (revised Jul 31 2026 — see below). Retrieval returns up to four chunks and they frequently share a section: the sample question on HF 719 returns Sec. 24 (Silver Lake), Sec. 24 (International Falls), Sec. 16 (Freeport), Sec. 24 (Cohasset). The mockup draws that as three near-identical cards, which reads as broken. One purple location chip per section, then all of that section's quotes stacked beneath it, each keeping its grant label and amount where the bill's text carries one. On that example: two cards, one holding three quotes and one holding one.

    **This replaces the original decision, which was to quote only the best-matching passage and say "+2 more passages in this section".** Design pushed back and the live data settles it: those three Sec. 24 passages are three *different grants*, so dropping to one would throw away two thirds of the evidence while the answer kept its claim. Grouping is about the LABEL — a reader should not see the same location printed three times — not about the quotes.

    **Deliberately not `citationsBySection`** (`apps/frontend/src/lib/billDetail.ts`), which the mobile bill page uses. That surface shows the section label *alone*, so a repeat carries no information and is dropped; here every repeat carries a different passage. The two rules are different on purpose, and that helper's own comment says so.

    **The rail explains why every quote stops early, on phone and desktop.** Directly under the "From the bill" heading row and before the first section chip, it says: *"Each quote is the opening of a longer section — open one to read it in full."* This line owns truncation only; the partial-coverage note above the answer owns how many passages the answer used.

    Grouped on the section's **anchor — id AND position**, not the id alone: `section_id_text` is not unique within a version (#854), so two genuinely different sections can share one and grouping by id would merge them into a single card.

    **The rail's input is capped at 8 passages, and that cap is what keeps "keep every quote" affordable** ([#868](https://github.com/alethical-org/alethical/issues/868), Jul 31 2026). This decision was written when retrieval returned four passages, so "keep them all" cost at most four quotes. A list question now *reads* far more of the bill (§4.4a) — HF 719 reads all 102 passages — and the first live run of that change served all 102 back, which this rule would faithfully have drawn as 102 stacked quotes. Reading and showing are different jobs: the synthesizer gets everything inside its word budget, while a citation is something a person checks the answer against, and a hundred is checked by nobody. So the served citation list is capped independently of what the answer was written from, and the "how much did we read" fact a long list was implicitly conveying is now stated outright in `coverage` (decision 11). Cite-or-refuse (`.claude/rules/grounded-answers.md` rule 1) asks whether a resolvable official source backs the answer, not how many do, so the cap never threatens it and never reaches zero.
2. **The bill card is the Search Bills result card component** (`apps/frontend/src/components/search/BillResultCard.tsx`), not a re-implementation. The handoff asks for the two to stay in sync; sharing the component makes that structural rather than a convention someone has to remember.
3. **The plain title is `ai_analysis.short_title`**, with the official "A bill for an act relating to…" title kept as the hover tooltip and screen-reader label only — the treatment `BillHeader.tsx` and the search card already use, per `.claude/rules/grounded-answers.md` rule 10.
4. **A cited-section card links to the passage in our own Bill Text tab** (`/bills/{id}?tab=text#ft-{sectionId}`), which `FullTextTab.tsx` already resolves, scrolls to and highlights — satisfying `.claude/rules/grounded-answers.md` rule 5. This requires the answer path's citations to carry the section id, which they do not today; the addition is part of #859. Where a section id does not resolve, the card falls back to the official source URL rather than rendering a dead link. This **supersedes** §9.2's two-link citation anatomy ("View in bill →" plus `revisor.mn.gov ↗`) for this page: the whole card is one in-app link, and the official record stays reachable from the page's source line and the bill page.

    **As built (#859) the fragment carries the section's POSITION as well as its id** — `?tab=text#ft-<section_id>-<source_order>`, the scheme [#854](https://github.com/alethical-org/alethical/issues/854) shipped (described in `docs/product-onboarding/bill-text-tab-spec.md` § "Jumping to a section"). The position is not optional: `section_id_text` is what the Revisor hands every section sitting outside an article, so 66 current versions repeat one id across several sections and 30 sections of `94-2025-SF3492` share `laws.0.1.0`. An id-only anchor lands on the first of those, which on a long omnibus is very likely the wrong grant — exactly the rule 5 failure the deep link exists to avoid.

    The Ask path's position is **exact**, unlike the bill page's key-point citations: a retrieval chunk holds its section's own foreign key, so no quote-matching is needed to work out which section a passage came from.

    The card builds its fragment with `citationSectionAnchor` and checks it with `resolveSectionAnchor` (both `apps/frontend/src/lib/billText.ts`) — the same helpers the Bill Text tab uses on an incoming fragment, so a link cannot promise a landing spot the tab would not honour. `passageTarget` (`apps/frontend/src/lib/askAnswer.ts`) then picks between three outcomes: the anchor **resolves** among the rendered sections → link to the passage; it **does not** → fall back to the official source, because retrieval may have run on a version a later re-read of the bill has moved on from and our text no longer carries the quoted passage; the sections are **still loading** → open the tab without an anchor rather than guess.

    The card is also a **real browser navigation**, not the usual in-app transition — React Navigation rewrites the URL on navigate, so an in-app transition drops the `#ft-…` fragment and the tab has nothing to scroll to.
5. **Generated wording is displayed, never recomposed, and the page prints NO COUNT.** The mockup's lead sentence ("Nineteen cities are named for infrastructure grants:") is a rewrite of what the model actually returns. Keep the model's sentence verbatim (rules 3 and 4).

    **The "a count may be a layout-owned label" half of this decision is withdrawn ([#868](https://github.com/alethical-org/alethical/issues/868), Jul 31 2026).** The flagship example is wrong at the source: for HF 719 the live answer names 19 cities and says no counties get named grants, while the bill itself names **98 cities and 20 counties**. Retrieval handed the answer writer four passages of a 48-section bonding bill, so the model enumerated what it could see. A count beside that list — even one derived honestly from the items on screen — turns an incomplete enumeration into a claim of completeness, which is the worst failure this product can make (rule 1). So: no count, no total, and no framing that implies the list is the whole set.

    *Those are the counted figures, replacing the "about 90 and about 16" this decision first carried.* Counted from HF 719's current version (48 sections, 15,430 words) with every questionable match read in context, twice and independently by two sessions in agreement: **98** distinct cities match the tight phrasing "grant(s) to the city of X", and **20** counties are named as recipients — 17 in the bare "grant to X County" form, which is where "about 16" came from, and 21 if the Moorhead-Clay County Joint Powers Authority counts, which is a joint-powers body rather than a county. Because the exact total turns on definitions the bill does not settle, both the eval and the regression test assert **lower bounds and named exemplars** rather than an exact figure, so they fail on a regression and not on a definitional argument. The counting method and every edge case live in `alethical/eval/ground_truth.py`, shared by both.
6. **The multi-column A→Z index is gated, and is layout only.** Apply it only when the answer's own list has ≥8 entries, each ≤32 characters, none reading as a sentence; otherwise keep the answer's order and shape. Re-ordering short names for scanning is a display choice; re-flowing sentences into a grid is not.

    Its one piece of layout copy is **"Listed A–Z"** — no number. The reader needs it because the names are no longer in the answer's own order, and it states a fact about the *layout*, never about the bill or about how many there are (decision 5). As built, the sentence test is *"does it end on sentence punctuation"*: inside a 32-character cap nothing longer than a short name phrase fits. Checking for a period *inside* the entry was tried and rejected — it flagged "St. Francis", one of the nineteen real HF 719 names, and a list of place names is full of abbreviations.
7. **"Ask another question" offers the bill's remaining `question_prompts`**, scoped with `scopedChipQuery` the same way Bill Detail scopes its chips, so a chip cannot dead-end in a refusal (rule 2). The cross-intent topic templates in `crossIntentChips` / `billTextChips` leave the bill, so they are second choice.

    **As built (#859) this is `followUpPrompts` (`apps/frontend/src/lib/askAnswer.ts`), NOT `askCardPrompts`.** Both read the same field and share the same `DEFAULT_ASK_CHIPS` fallback, but `askCardPrompts` is built for Bill Detail's Ask *card*: it holds prompt 0 back (it seeded the card's placeholder before the card became chips-only) and offers prompts 1–3 as chips. The reader arrives here having tapped one of those three, so reusing it would only ever leave **two** — where this decision says "offer the other three". `followUpPrompts` takes all four, drops the one just asked (matching past casing, spacing and the `HF 719: ` scope prefix), and caps at three. It also returns nothing until the bill's own prompts have loaded, so the block cannot show the generic fallback for a moment and then swap all three chips out under the reader.
8. **The session line comes from `bienniumEyebrow`**, which returns "2025–26 LEGISLATIVE SESSION" — not the served session name ("94th Legislature (2025 - 2026) Regular Session"), which is not the product's vocabulary. Regular bienniums use an en dash and shorten the second year; special sessions keep their single full year.
8a. **One date per page, and it lives in the source line** (correction to the handoff, Eugene, Jul 31 2026 — applies to web and mobile). The handoff's meta line read `2025–26 LEGISLATIVE SESSION · AS OF JUL 30, 2026` while the foot of the page carried "Updated Jul 30, 2026", printing the same date twice; and dating the *answer* overclaims, because an answer can never be fresher than the bill record it was generated from. So: **the header meta line is the session alone, with no date**, and the page's only date is the standard source line at the foot, unchanged in format — `Source: Minnesota Legislature · revisor.mn.gov · Updated {date}` — built by the shared `billSourceText` (`apps/frontend/src/components/billDetail/SourceLine.tsx`). The `{date}` is **the answering bill's own record date, the same value that bill's page shows**, never an answer-generation timestamp; take it from the bill, not from the Ask payload's `data_as_of` (which is the corpus-wide last successful ingestion, so it can post-date the record it is stamping — exactly the overclaim this rule removes). On mobile the same applies: the header's second date line beside Share goes, the session text stays. **No page-specific exception** — the general rule is recorded in `docs/design/ui-copy-guide.md` § Dates on a page.

    *Resolved Jul 31 2026:* the value is now a genuine per-bill pull date, so "Updated" means what a reader takes it to mean. The bill detail payload serves `last_pulled_at` (the ingestion run that last wrote the bill), and the one shared helper `pulledLabel` (`apps/frontend/src/lib/billDetail.ts`) turns it into the label for every surface that closes with a source line — both bill-detail screens and this page. Call that helper; do not read `bill.updatedAt`, which is the Legislature's last action and is what made the old line mislabelled. Remaining scope on [#861](https://github.com/alethical-org/alethical/issues/861): the two search screens, which still show the corpus-wide date in their results header.
9. **The refusal, NO MATCHES and vote-deflection states stay.** `?q=` is shareable and editable, so the page must still render them even though a chip cannot produce one. The handoff draws the answered state only.
10. **Share moves into the header** with Bill Detail's exact button and popover, copy-link inside the sheet. Layering is specified because it has shipped broken twice: wrapper `position:relative; z-index:60`, popover `position:absolute; z-index:1`, backdrop `position:fixed; inset:0; z-index:0`, and no competing stacking context on the body below.

11. **A partial-coverage note renders ABOVE the answer, from a served flag — never from the model's own prose** (decided Jul 31 2026, out of the [#865](https://github.com/alethical-org/alethical/issues/865) eval). Decided after the page shipped, so it is tracked separately: [#868](https://github.com/alethical-org/alethical/issues/868) serves the flag, [#883](https://github.com/alethical-org/alethical/issues/883) renders the note.

    On a long bill an answer is routinely generated from a fraction of the text and reads as complete. The eval measured what does and does not fix that, and the result rules out the obvious remedy: **a wider passage window does not make models honest.** Overclaim rate was flat at 80% with 4 passages, 89% with 8, 80% with 16; `gpt-4o-mini` given four times the text produced a *longer* list with a *stronger* completeness claim. Nine of nine models failed the completeness gate, and two of them made zero unsupported claims — they are not inventing anything, they are reporting what they were shown as everything there is. Full results: `docs/product-onboarding/answer-quality-bar.md` §9 (Passage budgets).

    Exactly one arm of nine volunteered that its list was partial, and even that sentence arrived at the *end* of a long numbered list. A reader's protection cannot rest on a behaviour one in nine models shows, in a position a skimming reader never reaches. So:

    - **Position: above the answer**, before the first line of prose. After the list it protects nobody, which is the whole point.
    - **Ownership: fixed UI copy owned by the layout** (§9.4, Fixed-copy elements; `.claude/rules/grounded-answers.md` rule 3). Never model output, never a string the model can influence. Keep asking the prompt for honesty as well — belt and braces — but never depend on it.
    - **Trigger: a served flag** carrying the fact, not a bare boolean, so the sentence can be specific ("draws on 4 of this bill's 102 passages") rather than vague ("coverage: partial"). Render nothing when the field is absent rather than guessing.
    - **Tone: quiet and factual**, matching the muted framing note on `topic_legislators` — not an error, not a warning. It accompanies a real, correct, cited answer.
    - **Still no count** (decision 5). If a count is ever shown, it may only be an "at least N" from a served lower bound, never a total counted off the items on screen.

    Why it matters most on this page: the flagship question the screen was designed around — HF 719's cities and counties — was answered from 4 of that bill's 102 passages, named 19 of the bill's 98 cities, and denied the counties it does name. The three-column index makes that list the visual centre of the page, so without this note the design amplifies a wrong answer.

    **The served fact, as built ([#868](https://github.com/alethical-org/alethical/issues/868)).** Optional on the `bill_text` answer, so the page renders nothing rather than guessing when it is absent:

    ```
    coverage: { used: int, total: int, enumerating: bool }
    ```

    `used` is the passages the answer was written from, `total` is how many the bill's current version has, and `enumerating` says whether the reader asked for *every* instance of something. The page composes the sentence from those three (`partialCoverageNote`, `apps/frontend/src/lib/askAnswer.ts`); the backend never sends prose.

    **`enumerating` exists because a complete read is not a complete list**, and that is the correction this decision needed within hours of being written. §4.4a now reads the whole bill for a list question, so HF 719 serves `used == total == 102` — and the answer still listed 26–35 of the bill's 98 cities. A page keying its caveat on `used < total` alone would therefore have dropped the note from precisely the answer that most needs one, as a *side effect of reading more of the bill*. So there are two sentences, not one:

    - **`used < total`** → *"This answer draws on 4 of the 102 passages in this bill, so there may be more it doesn't cover."*
    - **`used == total` and `enumerating`** → *"This answer draws on all 102 passages in this bill, but a list like this can still leave items out — check the bill's own text for the full set."*
    - **`used == total` and not `enumerating`** → nothing, which is where "a caveat on every answer teaches people to ignore it" still holds: on "when does this take effect?" there is no list to caveat.

    **`used` and `total` are counts of OUR passages and must never be rendered as counts of the bill's contents** — cities, counties, agencies. That would reintroduce the fabricated total decision 5 forbids.

    **The denominator is scoped exactly like retrieval** — current version *and* embedding model (`retrievable_chunk_count_stmt`, `alethical/db/models.py`). Counting passages retrieval cannot return inflates `total`, which makes a genuinely complete read report itself as a sample; that is the failure direction that silently removes the note, so the two statements are kept in lockstep and pinned by a test that seeds a stale version and a foreign-model passage.

**Shipped Jul 31 2026 ([#859](https://github.com/alethical-org/alethical/issues/859)).** Four things the build settled that are worth knowing before touching this page again:

- **"Bill Detail's exact button and popover" is now structural, not a convention.** `SharePopover` was lifted out of `BillHeader.tsx` into its own component (`apps/frontend/src/components/billDetail/SharePopover.tsx`) and both pages import it; only the sheet's own noun varies ("Share this bill" / "Share this answer"). The same move shares the cited-section card and the suggested-question chip: `CitationCard` / `SuggestedQuestionChip` (`apps/frontend/src/components/billDetail/CitationCard.tsx`), used by the Summary tab and by this page. The **web** Legislator Profile now imports it too, with `subject="legislator"` ([#874](https://github.com/alethical-org/alethical/issues/874)) — so three web surfaces share one control, and one of them was measurably not a pixel-copy before the fold-in: the profile's own button was 124×56 to the shared 111×46, and its panel was missing the Instagram icon. **The mobile Legislator Profile is deliberately not a caller.** Its Share is a `BottomSheet`, not an anchored popover, and its sheet body is byte-identical to the mobile Bill Detail sheet (`BillDetailScreen.tsx`) apart from the noun — so the mobile duplication is between those two screens and wants a shared *sheet*, not this component. A 366px-wide anchored panel does not belong on a 390px phone screen.
- **The layering is inherited, not re-specified.** The page is built on `SearchPageShell` (`apps/frontend/src/components/search/searchPieces.tsx`), whose gradient hero sits at `zIndex: 2` and white body panel at `zIndex: 1`. Share lives in the hero, so it paints above the answer by construction rather than by a rule someone has to remember. The shell's `heroEndsWithRule` is also what keeps the gap under the header hairline at the panel's own 40px instead of stacking to ~84px.
- **An eyebrow only appears where it is load-bearing** — the honest empty states (OUT OF SCOPE, NO BILL MATCHED, NO MATCHES) and the vote deflection's ANSWER + COMING SOON. An *answered* page carries none, on any intent: the question is the heading and the answer sits right under it, so "ANSWER" restates the obvious. The check for a `bill_text` answer must come **before** the no-matches check — `total_matches` counts matching bills for a *topic* answer and is always 0 on a single-bill answer, so the other order labels every answer "NO MATCHES".
- **The answering bill is fetched in full (`useBill`), not reshaped from the Ask payload.** Four things on the page come from the bill record rather than the answer: `BillResultCard` needs a whole `Bill`, the chips need its stored `question_prompts`, the card's Effective line needs the verified statutory date, and the source line needs the bill's own record date (decision 8a). The payload's own bill *is* used for the back link and the plain title, which is why `AskAnswerBill` now carries `shortTitle` — the vote deflection's card was printing HF 719's eleven-line statutory title, against `.claude/rules/grounded-answers.md` rule 10.
