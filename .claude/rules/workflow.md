# Session workflow rules

Machine-facing counterparts of the human conventions in `CONTRIBUTING.md`. Follow both; when they seem to conflict, CONTRIBUTING.md wins.

1. **Target branch first.** Establish at the start which branch or PR the work belongs to; work in your own worktree off `origin/main` for it (`just worktree <branch>` — mechanics in skill `when-to-act-without-approval`, concurrent-session safety; rule 10 carries the destructive-git prohibition) rather than building in the shared checkout. Don't build on a session branch and port the files later. Before starting new work, scan the open PRs (`gh pr list`) for the same files or topic — with parallel sessions, duplicating in-flight work means the same change merges twice and conflicts once (#121/#122). If an open PR already covers it, build on that branch or wait for it.

   **Scan the open *issues* too, not just the PRs — an issue is where in-flight guidance lives.** A PR scan finds duplicated *code*; it cannot find a decision. On Jul 28 2026 one session merged nine Dependabot PRs that an open issue ([#691](https://github.com/alethical-org/alethical/issues/691)) had explicitly said not to bulk-merge, singling out one of them as the likeliest to break production. That session had scanned open PRs, exactly as this rule said, and the issue was invisible to that scan. So before acting on work someone else may own — a batch of bot PRs, another session's area, anything with a tracking issue — also run `gh issue list --search "<file/topic>"` and read what it says. (The merge turned out to be correct on the facts, and its verification was better than the caution it overrode; that does not make the missed read harmless, because next time the issue will be right.)

   **`git fetch origin main` before you start building, and check *just-merged* PRs on your target file, not only open ones.** The session-start "N commits behind" snapshot goes stale the moment another session merges — origin advances mid-session. An overlap that already merged is invisible to an open-PR scan and surfaces only later, as a whole-file reformat or a merge conflict once you've built on a stale base. So before writing code: `git fetch origin main`, then `git log --oneline HEAD..origin/main -- <target file>` and `gh pr list --state merged --search "<file/topic>"`; if origin moved or a merged PR already touched the file, rebase and re-scope as an extension before you build (mobile ask-field, Jul 2026: #180 and #186 each merged mid-session and forced a rebuild).

2. **Commit and push at milestones, not at session end.** Uncommitted work is invisible — not in the PR, not reviewable, not recoverable by anyone outside the conversation. When a coherent chunk lands, commit it.

3. **Share branches, not file copies.** If the user hands you a loose copy of a repo file (Downloads, attachment), diff it against the branches before building on it — it may duplicate or trail a branch. Land durable content on a branch promptly, and point people at branches/PRs rather than exporting files. The moment a loose copy's content lands on a branch, delete the loose copy in the same session — a kept copy immediately starts trailing the branch and resurfaces later as a stale shadow of main.

4. **Route knowledge at birth.** Decisions → the relevant spec in `docs/`. Tasks and deferred work → GitHub issues, filed at the moment of discovery with: what it is · what exists today · why deferred · what unblocks it · **a milestone, an issue type, a topic label, and its board fields (Epic, Priority, LOE, Status)** (see the categorization rule just below) assigned at filing, not later (then cross-link the issue number back into the doc that spawned it). Product invariants → `.claude/rules/`. Team workflow norms → `CONTRIBUTING.md`. Chat is a scratchpad, never a system of record.

   **A decision reached in conversation, with no file changed, still ships a doc edit in the same session.** This is the case the rule kept missing, because every enforcement around it is code-shaped: rule 6's trigger is a change to observable behaviour, and `scripts/check_doc_sync.py` only runs on a PR that touches declared code. A session that settles something and writes no code trips *nothing*, so the routing has to be deliberate. The trigger to watch for is: **would the next session that asks this question have to redo the work to answer it?** If yes, it is a decision and it belongs in `docs/` now, not in the chat log.

   **The specific tell: reasoning that ends up inside a GitHub issue body.** An issue is the right home for *the task*; a doc is the right home for *why the alternative lost*. When you catch yourself writing a rejection rationale, a ranked-tradeoff list, or a "reconsider only if X" condition into an issue, that content is a decision wearing a task's clothing — put it in the doc and have the issue link to it. Jul 30 2026: a session evaluated model gateways and evaluation frameworks, reached four conclusions, and documented only the two that happened to ride along with code PRs. The rejection of Inspect AI went into [#787](https://github.com/alethical-org/alethical/issues/787)'s body and the ranked decision factors went nowhere at all; both had to be retrofitted after Eugene asked ([#792](https://github.com/alethical-org/alethical/pull/792)).

   The same applies to *existing* issues: when work you ship or a decision you record changes one — done, half-done, re-scoped, obsolete — update or close it in the same session. A periodic manual triage pass is the backstop, not the mechanism.

   **Categorize every issue at creation — the Roadmap board (org `alethical-org` Project #1 "Alethical Roadmap") is the source of truth.** An uncategorized issue is the exception to fix, never the norm. The full 8-axis scheme (Type · Milestone · Epic + Platform Track · Priority · LOE · topic labels · `research` label · Status), the two-step create-then-set-board-fields gotcha, the uncategorized-item sweep command, and the keep-the-board-current lifecycle rules all live in the skill **`file-github-issue`** — invoke it before `gh issue create`, when moving an item's Status, and when sweeping the board at session start.

   **Only ever set item field *values* and board membership — never restructure the project's fields, options, or views (this protects Eugene's saved Epic/Milestone/Board views).** The board writes a session is authorized to make are exactly four mutations plus the `gh` label/milestone flags: `updateProjectV2ItemFieldValue` (set an item's Epic/Priority/LOE/Status/Type/Platform-Track *value*), `addProjectV2ItemById` (put an issue on the board), `addSubIssue` (nest under a parent epic), and `unarchiveProjectV2Item` (before editing an archived item). **Off-limits without an explicit, in-session go-ahead from Eugene:** `createProjectV2Field` / `deleteProjectV2Field`, and **`updateProjectV2Field`** — the mutation that renames a field or **adds / renames / reorders / deletes a single-select option** (an Epic value, a Priority level, a Status column, a Platform-Track value, an Issue Type). Why it matters: Eugene's Epic, Milestone, and Board views are **grouped and sorted by these fields**, and grouping keys off each option's *identity and order* — so renaming, reordering, or deleting an option silently rearranges or empties his groups, which reads as "my board got reset." True view config (group-by / sort / visible columns / filters) is **not** writable through the public GraphQL API at all — it is saved per-view in the UI and only Eugene changes it — so a genuine layout reset can *only* come from an option/field restructure (or from uncategorized items piling into a "No Epic" / "No Status" group — the exact rot the two-step categorization + sweep in skill `file-github-issue` prevents). The 8-axis scheme is deliberately stable; when work seems to need a *new* Epic/option or a renamed field, **propose it to Eugene** and let him make the structural edit, then fill in item values — do not restructure the axes yourself. To defer or recategorize an issue, change its field *value* or move it to a higher-numbered milestone bucket (per the Milestone rule above); never rename or reorder the option itself.

5. **Verify cheap repo facts before deciding on them.** If a claim is one `diff`, `git log`, or `grep` away from certain (which version is newer, does the model have that field, is the file gitignored), check it before building work or advice on top of it. Scope and timing claims are the flagship case: never assign MVP/post-MVP or milestone timing from memory — check `gh issue list`, the milestones, and `docs/product-onboarding/product-scope.md` first, and cite the issue, milestone, or spec section that grounds the claim.

6. **After changing what a user sees or can do, search for everything that still describes the old behaviour.** Rule 4 covers artifacts you already know are affected; this rule covers the ones you don't.

   **The trigger is any change to observable behaviour, not only a "scope change."** This rule used to fire on scope decisions — re-scoping, re-phasing, renaming, drawing a boundary — and that framing let four real drifts straight through, because none of their authors would have called their work a scope change: an eyebrow label removed for a cleaner card ([#345](https://github.com/alethical-org/alethical/pull/345)), a filter description removed ([#709](https://github.com/alethical-org/alethical/pull/709)), URL filter serialisation shipped ([#135](https://github.com/alethical-org/alethical/issues/135)), one option added to a dropdown ([#607](https://github.com/alethical-org/alethical/issues/607)). Each made a documented sentence false. So the question to ask is not "did I change the scope?" but **"could a sentence someone wrote about this screen now be wrong?"** — which fires on ordinary implementation work, where the drift actually comes from.

   **Plain-English guides drift worse than specs, and are the ones to check first.** In every case above the spec was either updated or at least written by someone thinking about specs; `docs/product-onboarding/search-bills-guide.md` was updated by nobody and accumulated three outright false claims, including one asserting a transparency feature the product does not have. "Docs" means the user-facing guide too, not just the `*-spec.md` next to it.

   **This is now enforced, not just asked for.** Behaviour-describing docs declare the code they describe (`<!-- describes: <globs> -->`), and `scripts/check_doc_sync.py` fails any PR that changes declared code without one `Docs check:` line in the body. "None needed" is a valid answer — the check forces the *look*, not an edit. A doc joins the check by adding one comment line; frozen records (mockup handoffs, dated audits) deliberately declare nothing.

   **Editing the doc does not exempt you from the `Docs check:` line (tightened Jul 30 2026).** It used to: touching a declared doc skipped it entirely, on the reasoning that someone who already fixed the guide shouldn't have to also write a line saying so. That reasoning assumed an edit implies a read, and it doesn't. [#784](https://github.com/alethical-org/alethical/pull/784) added a batch queue to the enrichment runner and updated §4.1 of `docs/product-onboarding/ai-models-and-billing.md`; [#785](https://github.com/alethical-org/alethical/issues/779) added prompt caching and rewrote the same §4.1. Both passed on the strength of that edit, neither looked at §4 one screen above, and the guide shipped contradicting itself twice before [#786](https://github.com/alethical-org/alethical/pull/786) fixed it. **So read the whole doc, not the part you are editing, and say in the line what you concluded** — "Docs check: reread ai-models-and-billing.md §4 and §4.1; fixed §4" is the shape that would have caught it.

   **When you grep for stale text, grep for the claim your change falsified, not for the name of the thing you changed.** This is the reason the sweep above missed §4. A search for the feature name ("cache", "prompt caching") found only the paragraph being edited, because the false sentences never named the feature: they asserted a *status* ("the API path pays full list price", "*would* bill the same work at 50% off"). Two of the four carried a hedging word a pattern could find; the most damaging one was a flat assertion with no tell at all. No grep finds that — only reading the section does, which is why the enforcement above asks for a conclusion about the whole doc rather than trying to guess which sentences went stale.

   Whenever a decision re-scopes, re-phases, renames, or draws a boundary (descoping a capability, adding to out-of-scope, changing a DoD, changing terminology), actively *search* for artifacts that still describe the old state — `gh issue list --search "<feature keywords>"` for the tracker, `grep` across `docs/` and `.claude/rules/` for specs and rules — and update what the search finds in the same session, unprompted. Record the result in the PR body ("Stale-reference check: #79 rescoped" / "Stale-reference check: nothing affected") so reviewers can see it happened. The trigger is *making* the change, not being asked about it.

   `grep` can't see inside binary assets, so screenshots and diagrams embedded in any doc (build specs, onboarding guides, READMEs — not just `*-spec.md`) are the stale reference easiest to miss: when a change alters what a doc's screenshot depicts (copy, layout, states, chips), refresh the embedded image in the same change so the doc's visual and text never diverge. A chat-attached image isn't a file on disk — locate the source (screenshots land in `~/Desktop/Screenshot/` as `.jpg`), verify it's the right frame, and convert to match the tracked asset's format (`sips -s format png`) so the path stays stable. For a **diagram** the doc ships as both an editable `.svg` and a rendered `.png`, editing the SVG leaves the PNG stale, and the usual converters (`rsvg-convert`, `inkscape`, `cairosvg`, `magick`) are not installed here — macOS always has Quick Look: `qlmanage -t -s <px> -o <outdir> file.svg` renders faithfully. Reach for it rather than downgrading the refresh to a follow-up.

7. **Name things so a newcomer can guess what they are.** Branch names, PR titles, filenames, headings, and rule names describe the thing literally, in plain words: `docs/update-issues-on-scope-change`, not `docs/ripple-sweep-habit`. No metaphors, coined terms, or shorthand that only makes sense to whoever was in the conversation that produced it. Name for what the change *does or decides*, not for where it lands — the diff already shows the location. If a coined term genuinely earns its keep, define it in plain words at first use in the doc that owns it.

8. **Spell out spec references — file name plus section topic.** When citing a spec section in any artifact (docs, issues, PR bodies and comments, chat), write the full spec file name and what the referenced section is about — its header or topic: "`docs/product-onboarding/grounded-ask-spec.md` §9 (Answer page UI — v1 states)", never "the spec §9" or a bare "§9.4". Someone new reading the sentence in isolation should know exactly what's being referred to without opening anything. Once the full form has appeared in an artifact, later mentions there may shorten. The same principle applies to every pointer: issues and PRs get markdown links with their titles or a gloss, never a bare number.

9. **Resolve factual claims from the primary source, yourself.** When a fact that will be shown to users or baked into product content, copy, or a mockup can be confirmed from a primary source — a bill's enacted text, a statute section, an official roll-call record, an authoritative page — fetch and read that source and confirm the exact value (effective dates, verbatim quotes, section/subdivision numbers, vote tallies) before asserting it. Don't relay a secondary summary, trust a skim, or hand over an unverified value with "please confirm" — do the digging and resolve it. When sources conflict (e.g. a status-page metadata field shows one effective date but the enacted bill's EFFECTIVE DATE clause shows another), the authoritative primary text wins; state the discrepancy and which source you trusted. This extends rule 5 from repo facts to external primary sources, and it matters most for anything user-facing, where a confident-but-wrong cited fact is the worst failure (`.claude/rules/grounded-answers.md`).

10. **Just do safe, reversible work — act, then report; don't propose-and-offer.** The test is **blast radius + reversibility + verifiability** — never who thought of it, how big it is, which lane it sits in, or how late in the session it is. If a change is safe, reversible, and you can verify it: build it, verify it, ship the whole loop (branch, commit, open the PR, squash-merge, then `git fetch origin main && git reset --hard origin/main` so no local branch is left pointing above main and resurfacing as a stale "Create PR" prompt), and report the result. This covers docs, specs, `.claude/` rules and config, issues, **and app / front-end / backend / production code**. Rules 1–2 still apply — right target branch, scan open and just-merged PRs first. Zero-behavior cleanup (a stale comment, a typo, a broken cross-link, a reference your own change orphaned) is always in-lane, in any file, including code another session just shipped — correct it, don't offer to. This is the referent for `coding-discipline.md` rule 1's "those autonomy norms stand."

    **Standing autonomy grant (Eugene, Jul 14 2026).** Every category these rules once marked propose-first — schema/data migrations, auth/security, outbound communications, production-data runs, outward-facing content, capability copy — is now act-then-report. "It's propose-first" is **no longer** a reason to pause; where any other clause in these rules says otherwise, this supersedes it. Four grants follow from it, each standing on its own:

    - **Merge your own low-risk PRs yourself, then summarize** — CI-green, cleanly `git revert`-able, behavior verified (tests + dev-server QA as applicable), degrading safely. Don't hand it back with "want me to merge?"

      **"CI-green" means green against the *current* `main` — re-run the checks if `main` has moved since they ran.** GitHub calls a branch mergeable when no *text* conflicts; it says nothing about whether the two changes still agree in meaning. So a stale green is not a weaker signal, it is a signal about a base that no longer exists. Check with `gh pr view <n> --json mergedAt` on what has landed since, or just compare the check run's timestamp to `git log -1 --format=%cI origin/main`; if `main` moved, `gh pr checks <n> --watch` after a rebase before merging. Aug 5 2026: [#990](https://github.com/alethical-org/alethical/pull/990) (stop the auth read path writing on every request) merged on four-hour-old green checks, and [#1020](https://github.com/alethical-org/alethical/pull/1020) had since added a test asserting the exact write it removed. Different files, no conflict, both green alone, **red together** — `main` was red for ~30 minutes and nothing else could merge. Reviewing either diff could not have caught it; only re-running could. This is deliberately a checkable step rather than "merge carefully", which is not checkable (framing proposed by the session that had to clean it up).

      **And `gh pr checks` itself lags a force-push, so the command this rule just told you to run can hand you the stale green it was meant to catch.** Aug 6 2026: after rebasing [#1097](https://github.com/alethical-org/alethical/pull/1097) onto a `main` that had moved, `gh pr checks 1097 --watch` returned **completed, all passing** — for the *previous* run, on the commit that had just been replaced. Querying the new head directly showed `changes` and `doc-references` still `in_progress` and `frontend` not started. Trusting the PR view would have merged on green belonging to a commit that no longer existed, which is the same class of failure as merging on a stale base, one level further in.

      So verify against the **head SHA**, not the PR: `gh api repos/alethical-org/alethical/commits/$(git rev-parse HEAD)/check-runs`. To wait, poll that until nothing is unfinished — `until [ "$(gh api .../check-runs --jq '[.check_runs[]|select(.status!="completed")]|length')" = "0" ]; do sleep 10; done` — then read each `conclusion`. `main` moved 4 times during that one PR, so on a busy night this is the difference between a real green and a remembered one. The general rule: **the convenient view is the stale one.** `gh pr view`'s mergeable flag, `gh pr checks`' summary, and a session-start "N commits behind" snapshot are all caches; git refs and the commit's own check-runs are the facts.
    - **An additive, reversible, verified migration is auto-merge** — `CREATE TABLE`, a nullable column, an index, a new enum value — proven by an upgrade→downgrade→upgrade round-trip against real Postgres plus CI green. `migrate.yml` auto-applying it to production on merge **is** the deploy path, not a gate. A dry-run-proven, idempotent backfill is likewise auto-merge.
    - **Paid production runs are authorized** once you have established that no zero-cost path suffices. **Cost alone never gates** — wherever any clause here lists money or spend as a reason to pause, this supersedes it.
    - **Applying `workflow-overhead-audit` verdicts is in this lane**, including meaning-preserving rewrites of a rule or skill file.

    **You are in the lead on this platform's product management and engineering (Eugene, Jul 16 2026).** Identify, prioritize, and sequence the work yourself and carry it to done; don't wait to be pointed at each piece. When a task names a goal or an area but not a step list, enumerate the items, order them unblocked-and-highest-value first, and work through all of them.

    **THE HARD LINE — the one thing that actually stops a build.** Never let a build *fire* an irreversible external side effect unverified: a real send to real users, spending real money on an unverified run, or a destructive/irreversible production data / schema / access change. This is honored by **engineering, not by asking**: build the capability fully, keep the live/irreversible trigger behind config (env/flag, dry-run default off), and verify with tests plus a dry run and a scoped single-record live check read back — so the work ships autonomously without an unverified live blast. An *additive, reversible, verified* migration or backfill is **not** this.

    **Reserved stops — exactly two, alongside the hard line above.** (1) A genuine **toss-up**: no basis to prefer an option, so surface it briefly and lead with a recommendation, never a bare menu. (2) A genuine **correctness / verification gate you cannot establish** — which means *investigate* the gate (measure it, read the source, sample the data) and act on what you find; never "stop because a gate might exist."

    **Not valid reasons to stop — every one of these has cost a needless handback.** It wasn't explicitly requested · *you* recommended it rather than the user · it's a big build · it's polish rather than critical path · it's backend code / app code / production code · it's late in the session, or your context is filling · "this is better as a fresh session" · it's another session's code · it sits in a later milestone · a task prompt said "propose-first" (read that as *verify especially carefully*, not *stop*) · a fancier gated option exists beside your safe one (ship the safe one now, flag the gated one separately). Ending a turn with "want me to…?" or "say the word and I'll…" for something safe and reversible **is** the handback this forbids — your recommendation *is* the go, and a proposal is itself a safe deliverable, so produce it rather than offering to. On a real blocker, say so in one line and immediately switch to the next-best unblocked work rather than idling.

    **The category is writes into a shared checkout, not git commands — and that is a wider category than every bullet below implies.** Each rule here names a git command, which quietly teaches that non-git commands are safe. They are not. `cd /Users/eug/Code/Alethical` followed by `cat >> file`, `> file`, `sed -i`, `rm`, or running a formatter writes into everyone's shared tree, and **no hook, lock, sandbox or rule in this repo guards any of them.** Aug 3 2026: a session working #100 ran several commands after a `cd` into the shared checkout and appended a file there. What saved it was luck of the operation, not any guard — the write was append-only, so `git diff --stat` proved it was `197 added, 0 removed` and entirely its own. A `sed -i` or a `>` produces a diff with deletions in it, and then you cannot tell your write from a teammate's uncommitted work. **Check your working directory before any write, not only before a git command**, and prefer an absolute path into your own worktree over a `cd`. Recovery, if you do write there: prove the diff is purely additive and entirely yours *before* touching anything, move the content into your worktree, then `git checkout HEAD -- <path>` scoped to that path — never a blanket reset. (The same session reported this unprompted after catching itself, which is the only reason the gap is written down.)

    **Never run destructive or branch-switching git on a shared checkout.** `git reset --hard`, `git checkout .` / `git checkout -- .`, `git clean -fd`, discarding a stash, and `git checkout <other-branch>` on a checkout other sessions may be using will **silently wipe their uncommitted work** and yank the branch out from under them — this has actually happened (Jul 2026: one session's cleanup `reset`/`checkout` wiped two other sessions' in-progress edits). Inside your own worktree these are safe. If you must touch a shared checkout, only ever *add*, never discard.

    **Three more that read as harmless and are not — each cost a real incident on Jul 30 2026, all in the same night.** The list above is about commands that obviously discard. These don't look like they discard anything, which is exactly why they got run:

    - **`git stash` — creating one, not just dropping one.** A stash in a shared checkout scoops up *whatever every other session has in flight*, and popping it re-applies that older snapshot on top, silently moving merged code **backwards**. One session stashed to build a before/after baseline and un-merged another session's just-shipped production fix (the [#756](https://github.com/alethical-org/alethical/pull/756) decimal guard) along with its spec edit. **To compare against another revision, never touch the working tree: `git show origin/main:<path>`.** That reads the file straight out of the object store.
    - **Moving a branch another checkout has out — now blocked by git itself, so the residual is `git update-ref`.** `git checkout -B <branch>` used to be the hole: on the Apple git this Mac shipped (2.39.5) it printed `Switched to and reset branch`, moved the ref, and left the other checkout pointing at a commit its branch no longer named with its uncommitted edits still on disk. **git 2.44.0 closed it** (`die_if_switching_to_a_branch_in_use()` in `builtin/checkout.c`, absent in v2.43.0, present in v2.44.0), and `git` on this Mac's `PATH` is now Homebrew's 2.55.0, where the same command dies `'<branch>' is already used by worktree at <path>`. Verified side by side on Aug 3 2026, old binary against new. So on a current git, `checkout`, `switch`, `rebase`, `branch -f` and `branch -D` all fail safe.

      **Three ways that guard is still absent, all verified on 2.55.0 — do not read "git blocks this now" as "this cannot happen".**

      - **`git update-ref` has no guard, in any version.** `git update-ref refs/heads/<b> <commit>` moves a held branch silently with no output at all, and `git update-ref -d refs/heads/<b>` deletes one, where `git branch -D` refuses. Deliberate: plumbing carries no safety checks. So this stays a rule, not a mechanism — never point `update-ref` at a branch you do not own.
      - **`git checkout --ignore-other-worktrees -B <branch> <commit>` defeats the 2.44 guard in one flag.** Measured: plain `-B` died `already used by worktree`, the same command with the flag printed `Switched to and reset branch`, moved the ref, and left the victim worktree's HEAD jumped with its uncommitted edits still on disk. This is the trap this whole rule keeps describing — a refusal teaches you the name of the override. Treat the flag as off-limits on a branch you do not own, the same as `--force --force` on a locked worktree. (Found by a Cursor review, Aug 3 2026, then reproduced directly.)
      - **The old, unguarded git is still installed.** `/usr/bin/git` is Apple's 2.39.5 and still resolves; only the `PATH` default moved. A script, launch agent, CI step, or tool that calls `/usr/bin/git` by absolute path gets the version where plain `-B` silently moves another worktree's branch. Do not write "this Mac runs 2.55" — write which git, invoked how. Apple's copy cannot be removed, so this one is permanent. (History: this bullet first grouped `-B` with `git branch -f` as if both moved the ref — `branch -f` never did. Corrected Aug 3 2026 after a Codex review flagged it, both cases were tested directly, and the upgrade made most of the bullet moot.)
    - **`git worktree remove --force <path>` deletes a worktree *and* its uncommitted work, in one command.** No git version guards this, and "clean up stray folders" is a plausible thing for an agent to try. The mechanism that stops it is a lock: `git worktree lock <path> --reason "..."` makes the command die `cannot remove a locked working tree, lock reason: ...` and print the reason back. A second `--force` still removes it, which is the deliberate escalation, not the accident. Locking does not interfere with the locked worktree at all — commits, status and history all work normally, and `git worktree prune` leaves it alone. **The locking is automatic: `.githooks/post-checkout` locks every new linked worktree as it is created**, whichever tool ran `git worktree add`, and `just worktree-rm` unlocks before removing so the intended cleanup path is unaffected. `post-checkout` was chosen over a `reference-transaction` hook deliberately — it never inspects refs, so it cannot misfire during `git gc` or `git pack-refs`, which is exactly what killed the reference-transaction attempt (Aug 3 2026: that hook blocked both ref attacks and also blocked routine packing, because packing reports each branch as a create then a delete and the two are indistinguishable without backend-specific storage inspection).

      **Say what this does not cover, because it reads stronger than it is.** The hook only covers worktrees created *after* it is installed; `git worktree remove --force --force` still removes a locked worktree; `git worktree unlock <path>` clears the lock; and none of it works until someone runs **`just install-hooks`** in that clone, because `core.hooksPath` is local config and git cannot ship it inside a repository. **A fresh clone is unprotected.** The recipe deliberately sets an *absolute* hooks path pointing at the main checkout's `.githooks`: a relative path resolves per worktree, so a worktree checking out a branch that predates `.githooks` would silently get no hook (found by testing, Aug 3 2026, before this shipped). The hook file must stay mode `100755` — git warns `hook was ignored because it's not set as executable` and carries on, so a lost executable bit disables this silently. The 7 worktrees live on Aug 3 2026 were locked by hand.

      **And treat all of it as bounded loss, not prevention — tested against a live agent, the lock is an approval prompt.** On Aug 3 2026 a Cursor IDE session ran the four commands no git version guards, with its sandbox on and its own deny rules loaded. Every one surfaced as an approval prompt rather than a denial, and every one *succeeded after approval*: `git update-ref` moved a held branch, `git update-ref -d` deleted one, `git checkout --ignore-other-worktrees -B` overrode the 2.44 guard, and `git worktree remove --force --force` deleted a **locked** worktree. Its `permissions.deny` entries bound only the separate `cursor-agent` CLI, never the IDE agent. Two things did hold with no prompt offered: the `.cursorignore` fence (refused for both an editor write and a shell write) and git's own 2.44+ refusal, which has no approval path. So with an agent that can request approval, **no configuration is a wall**, and the honest goal is that losing work costs at most a few minutes rather than everything.

      That is what **`just install-wip-backup`** provides: every 5 minutes, each worktree's uncommitted work is captured into a `refs/wip-backup/<worktree>` ref plus a thin bundle outside the repo (`scripts/back-up-uncommitted-worktree-work.sh`). It stages into a temporary index so no worktree's own index is touched, it pushes nothing because this repo is public and uncommitted work is unreviewed, and snapshots survive both worktree deletion and `git gc`. Costs nothing per run. The prompting case: an audit of production schema drift was found on Aug 3 2026 existing as one uncommitted file in one worktree, referenced by nothing, after the session that wrote it had stopped.
    - **Creating a branch in the shared checkout at all.** It yanks that checkout off `main` while another session is using it. Branch in your own worktree (`just worktree <branch>`).

    The generalisable rule: **in a shared checkout, treat the working tree and every ref as someone else's live state.** Read from git's object store, write only in your own worktree. And when you do disturb one, verify before repairing — prove the tree matches a known commit (or that the branch point contains the other session's work) *before* restoring anything, then use `git restore <path>` / `git checkout <commit> -- <path>`, never a blanket reset. Both sessions that hit these did exactly that and lost nothing; the damage stayed inside a working directory and never reached `main` or production.

    **Per-domain verification checklists** — front-end, backend, migrations, paid runs, unreachable-code removal, sweep-the-pattern and solve-the-broader-problem scope, and the concurrent-session commit/merge mechanics — plus the incident history behind each grant above: skill **`when-to-act-without-approval`**. That skill carries what to *verify*; the authority is resident here, so a change is never held for approval merely because the skill wasn't loaded.

11. **Lead issues, PRs, and substantive comments with a plain-language "Net:" line.** Every GitHub issue, PR body, and substantive PR/issue comment opens with (or clearly labels near the top) a one–two-sentence **Net:** — the bottom line in plain words a non-specialist maintainer can act on: *what it means / what to do / why it matters*, not the mechanism. The full technical detail still follows in the body; the Net line is the layer that makes the takeaway graspable at a glance without parsing the internals. Same convention as the "Net:" line on decision options and chat wrap-ups (`~/.claude/CLAUDE.md`; memory `options-include-effort-and-reasoning`). A reader who only reads the Net line should still come away knowing the point and the ask.

   **Two levels, not one.** Beyond the overview Net at the top, **every acceptance-criteria (or checklist) item carries its own inline `— Net:` gloss** next to its technical wording — the plain-language *what this means / why it's checked* for that specific item — so the list is legible to a non-specialist line by line, not only in aggregate. Keep each item's gloss to a short clause; the technical criterion stays (it's what's verified), the Net just complements it. When editing an existing issue/PR that predates this, retrofit both levels. This applies to the issues and PRs *you* author or own; don't rewrite another session's merged artifact — add a Net comment there instead.

12. **Expensive background research is checkpoint-and-resume — never let it run into paid overage (Eugene, Jul 18 2026).** Multi-agent research runs (deep-research and similar Workflow fan-outs) are the costliest thing a session does, and **any of the usage meters can run out mid-run — the 5-hour session window, the weekly all-models allowance, or the weekly per-model allowance.** Checkpoint at launch, stop the run (`TaskStop`) before a meter hits its limit rather than burning into overage, and resume from the journal cache. **Never promise a threshold stop without arming a mechanism** — Claude cannot see the meters and does not run between turns. Full mechanics (checkpoint contents, byte-identical `args` resume, journal cache, cheap tails, armed one-shot stops): skill **`resume-research-workflow`**.

13. **Staff every goal-supporting issue — delegate the ones you're not doing yourself; milestone never gates this (Eugene, Jul 22 2026).** When a goal touches more than one outstanding issue, *every* issue that supports reaching that goal must have an **active owner** — this session, or another session you've prompted — never sitting unstaffed in the backlog. As you work a goal, enumerate the issues it depends on or spins off (including the durable/source fixes behind any interim patch you shipped, and the honest fix behind any design item you declined), and for each one either **work it here**, **confirm a running session already owns it**, or **prompt a fresh session to take it** — `spawn_task` a self-contained, direct-address brief (or `send_message` an existing session), telling it to coordinate back via the issue's comments, exactly as done for #483 / #520 / #550 / #551. Leaving a goal-supporting issue with no owner — "filed, parked, someone will get to it" — is the failure this prevents; the maintainer put you in the lead, and coverage is the lead's job. After delegating, **monitor** the sessions and **finish any dependent integration** yourself.

    **Always tell a delegated session to `send_message` you back the moment it finishes (Eugene, Jul 22 2026).** Every delegation brief (`spawn_task` / `send_message`) must end with an explicit instruction: *"when you're done — PR merged or work blocked — `send_message` this session (name + id) with the outcome (PR #, merged/blocked, anything I need to integrate)."* Do NOT rely on the background task-completion notification to learn a delegated issue shipped: that fires only when the session's *process* ends, which lags — often long after the PR merged, sometimes never within your turn — so a merged issue can sit uncaught until you happen to poll GitHub (Jul 22 2026: #520 merged via #567 and I only noticed on a manual sweep, because I'd received the "started" ping but no timely "finished" one). The direct message arrives in-thread as a user turn, so you can immediately confirm the work, run dependent integration, or restaff on a block — instead of discovering it late. Include this session's own identity in the brief so they know who to message.

    **A blocker only a fresh session can clear is a staffing job, not a status report (Eugene, Jul 30 2026).** When you work out that the way past a blocker is "a new session has to do this" — a setting that only takes effect on restart, a permission gate this process can't clear, auth or a tool this session lacks, a context window too full to finish — then **starting that session is the work**. `spawn_task` a self-contained brief immediately, without asking; a chip the maintainer has to click still gives the work an owner the moment he looks, so file it rather than skipping it because it isn't fully hands-off. Ending a turn with "start a fresh session and run this script" is the handback this forbids: you diagnosed the mechanism and then made the maintainer operate it. Then carry on with everything the blocker doesn't touch. (Jul 30 2026, [#723](https://github.com/alethical-org/alethical/issues/723): the permission classifier refused the paid re-enrichment run ~8 times; the session correctly identified that only a restarted session would clear it, then told Eugene to restart and run it himself instead of spawning the session that would have.)

    **Milestone is irrelevant to staffing — `v1`/`v2`/`v#` mean nothing for whether work gets done now (Eugene, Jul 22 2026).** Milestones only *group and report* work; they are **not** a defer signal. Never leave a goal-supporting issue unstaffed, or decline to pull it forward, *because* it sits in a later-numbered milestone — if it supports the goal at hand, staff it now regardless of its bucket, and re-milestone it if the bucket no longer reflects reality. This **overrides** any earlier phrasing in these rules that reads a higher-numbered milestone as "deferred / do later" (e.g. rule 4's phase language and the "defer by moving to a higher bucket" note): those describe how milestones *label* phase, not a license to leave goal work unowned. When you catch yourself about to park a supporting issue as "it's v2," that thought is the trigger to instead give it an owner.
